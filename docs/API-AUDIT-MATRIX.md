## HTTP semantics and limits

Observed: 200 for successful reads/most CRUD, 201 for orders/messages, 400 for invalid input, 401 for missing/invalid authentication, 403 for forbidden/suspended, 404 for missing single records, 413 for oversized files. Duplicate database uniqueness violations now map to 409. Infrastructure/schema errors remain sanitized 503. The application deliberately uses 400 rather than 422 for schema validation and 503 rather than leaking raw internal exceptions as 500.

Unsupported DELETE/PATCH actions now return 405 instead of falling through to mutation handlers. Deep unknown paths return 404. This is not a claim that every unsupported verb/path permutation was exhaustively tested. Successful DELETE of no visible rows may return an empty array (idempotent deletion); this does not disclose whether another user's record exists.

Negative coverage includes malformed JSON, missing fields, bad UUIDs, invalid coordinates, wrong password, forbidden role, forged ownership/approval, private-data reads, cross-origin mutation and invalid carts. Provider email failure handling was inspected; a real outage was not induced. API pagination exists, but exhaustive multi-page datasets and every filter combination remain NOT VERIFIED.
